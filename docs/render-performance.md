# Rendering performance

## Dropped items

The original optimizer only limited decorative copies within a stack during submission. It did not reduce model extraction for a single dropped block or the terrain/light queries used to build each shadow.

The item optimization setting reuses static ground item models, including their bounding boxes. The cache is limited to 256 model identifiers, isolated by world, validated against the current baked model object and cleared on resource reload. Exact vanilla cuboid models without tint qualify, including generated tool models. Their only stack-dependent input is foil selection, cached separately as none, standard or special. Enchantment/name/damage components therefore do not exclude otherwise static geometry; glint and atlas animations remain active. Conditional, custom and world-tinted models use vanilla extraction. Each entity still keeps its own position, animation, light, stack count and seed.

Ground-item main-pass submission acquires a vertex consumer once per consecutive material run. Runs preserve quad order and stop at every render-type change; render types that cannot consolidate geometry keep individual submissions. With Sodium 0.9.2 or newer, supported consumers receive up to 64 quads per native vertex push, using at most 9 KiB of stack scratch space. Packed normals are reused within the same pose. Sodium still owns format conversion and upload, including Iris extended vertices. Unsupported consumers and installations without Sodium retain `putBakedQuad`; outlines and foil passes retain their original paths. This does not remove entities or reduce their geometry.

The separate item-shadow setting skips shadow extraction beyond 8 blocks when visible item count reaches the threshold (64 by default), or beyond 4 blocks at twice the threshold. The preceding extracted frame supplies density, so activation is delayed by one frame and does not rescan all loaded entities. World changes and disabling the setting reset the budget. Item models remain visible, and other entity shadows retain vanilla behavior. Client entity ticking and server TPS are unchanged.

`verifyItemRendering` and `verifyItemVertices` are included in `check`. They check density/distance boundaries, reset and thread isolation, the 26.2 hook/cache/buffer contracts, and 7,872 packed vertices against Sodium's actual encoder. Vertex cases cover rotated, mirrored and nonuniformly scaled poses, per-vertex color/light, emission, normal-cache overflow/reset and batch boundaries. Fifteen Iris conversion cases compare individual quads with batches, including item/entity IDs, tangents and mid-UV. These checks do not measure item FPS.

A separate local Fabric pre-launch smoke check loaded the configured runtime mods and confirmed application of the item submission/cache mixins, Sodium's quad interface and widened pose-normal access. It exited before entering Minecraft; no game window or world was used for that successful check. This verifies hook loading, not in-game rendering or resource-pack behavior.

A 30-second JFR sample of the running development client on 2026-09-27 contained 1,770 render-thread samples. The main item submission path appeared in 893 samples, Sodium quad encoding in 598, vertex-consumer acquisition in 260, and item model bounding-box calculation in 112. These inclusive counts overlap and are not wall-clock percentages. GC pauses totaled about 92 ms. The server thread was largely paused during this capture, so it is evidence for the render bottleneck, not a server-tick benchmark. Raw recordings remain local because they can contain process/environment metadata.

`benchmarkItemVertices` compares the installed Sodium encoder with the batch encoder on 512 items × 64 quads, including native staging copies. It alternates execution order, warms up 15 rounds and measures 31 rounds. Local median CPU time was 3.698 ms versus 2.375 ms (35.8% lower). This excludes GPU rendering, model resolution and consumer acquisition; it is not an end-to-end FPS claim. Test the rebuilt client after restarting, in the same scene with the same resource/shader packs and item optimization enabled.

## Blaze3D UI and glass

The production UI uses Blaze3D for all GPU work: texture ownership, glyph/image uploads, transient vertex/uniform buffers, scene copies and RenderPipeline/RenderPass draws. No production class references LWJGL OpenGL, Blaze3D's OpenGL backend classes, Skia DirectContext or backend render targets. The legacy Skia drawing facade and RenderSkiaEvent remain so existing HUDs and screens keep their layout and event registration. Their canvas is now UiCanvas.

Rounded rectangles, strokes, arcs, gradients, clipping, shadows and glass are GPU primitives evaluated by the UI shader. Transform and clip state is recorded per draw; adjacent glyphs on the same atlas share a vertex batch. Skia is retained only for CPU font metrics, glyph rasterization, image decoding and exported CPU specimens. Glyphs are rasterized once per font/scale and uploaded into 1024-square atlases; artwork is uploaded once per image. Ordinary frames upload geometry and uniforms, without rasterizing or uploading the entire UI. Atlas and artwork caches are bounded and released before the rendering device closes. Borrowed Minecraft textures, including capes, are sampled through GpuTextureView and never closed by the UI.

Upright text is hinted and rasterized at its actual device font size (quantized to 1/64 pixel for cache reuse). Glyph origins are aligned to screen pixels, and atlas texels are sampled one-to-one, retaining grayscale antialiasing without a second bilinear filter. This includes fractional GUI scaling and translations inside opacity groups. Rotated or nonuniformly scaled text retains transformed geometry with smooth sampling. Skin heads, full skins and cape previews explicitly select nearest-neighbor sampling; ordinary artwork keeps linear sampling. The image sampling mode participates in batch separation, and opacity layers composite one-to-one with nearest sampling.

A transparent RGBA8 UI target is composited with premultiplied alpha before GpuSurface.blitFromTexture, submission and presentation. The destination size drives allocation and the root scale, including RGSS. Resizing replaces frame-size targets while retaining the glyph/image cache. Recording fails before touching the destination, so a broken callback leaves the original game frame intact.

Glass captures the original scene once through copyTextureToTexture when enabled. Panels sample that shared copy rather than preceding text or overlapping controls. The shader treats scene RGB independently of its alpha, so valid alpha-zero scene colors do not become brighter. Blur/refraction use local UI pixels, transformed back to full-frame scene coordinates. Animated opacity uses bounded GPU layer textures and blends overlapping contents once. Glyph and sprite sampling is clamped to each source rectangle to prevent neighboring atlas entries bleeding into it. Cover-art blur is evaluated by the shader in local UI pixels.

There is no backend-specific fallback or native GPU state boundary. The public Blaze3D path was tested on the installed OpenGL backend; the complete client has not yet been tested with Vulkan, the user's server scene, or their resource/shader packs.

verifySkiaInterop is included in check. It verifies the 26.2 presentation timing and scans every production class for forbidden backend-specific GPU access. verifySkiaInteropGpu creates a hidden real Blaze3D device and checks composition/orientation, untouched scene pixels, rounded/difference clips, transformed coordinates, opacity groups, gradients, glyph outlines against a CPU reference, cached text/artwork, failed callbacks, resize and borrowed-texture ownership. Additional sampling checks compare small Latin/CJK glyph coverage against direct native rasterization at 75%, 100%, 125%, 150% and 200% scale, with fractional translations and opacity layers. Pixel-art checks exercise both cropped CPU images and borrowed GPU textures at those scales, with smooth artwork in the same frame to catch sampler/batch confusion. verifyGlassGpu checks scene-only sampling, constant RGB with alpha zero/one, transformed clipping, opacity groups, disabled capture and full-frame coordinates. GPU tasks are optional for CI hosts without a graphics device.

previewBlazeUi exports the real Material controls through the production GPU path and a separate blaze-quality-preview.png with pixel art and small text at several scales; previewMaterialTheme keeps the independent CPU compositing specimen. benchmarkGlassGpu renders 12 representative HUD panels at 2560 x 1540, with/without a 600 x 400 menu and glass. It warms up 30 frames and measures 120 per case using cached bundled glyphs. CPU timings cover recording/uploads/submission and exclude timer-result waiting; GPU timings use native timer queries confined to the verification source set. The fixed-order microbenchmark is diagnostic, not a before/after comparison or game FPS prediction. World load, other mods, resource packs and display scaling require a same-scene in-game comparison.

A local Fabric pre-launch smoke check with the configured mods, including Sodium and Iris, confirmed that the UI presentation mixin still applies after migration. It exited before Minecraft initialization and did not enter a world.
